# Spec — CRS Slots (A/B): slot header, flash layout and boot selection

Status: **normative**. Applies to: the firmware's slot reader (`kb_firmware/src/config/loader.rs`), the firmware's slot writer (WebHID "Save to device", `kb_firmware/src/config/slot_writer.rs`), and SWD flashing from the host (`crs-pack pack-slot`, `tools/embed_with_cfg.sh`).

Purpose: a small slot header that wraps the fixed **CRS v1 blob (288 bytes)** so that two copies can live in flash and the newest valid one is chosen at boot. The slot format doesn't depend on how the slot was written (SWD or WebHID).

> The firmware writer's power-loss-safe order is specified in [§8.3](#83-writing-a-valid-slot).

---

## 1) Overview

- A **CRS v1** blob is **288 bytes** (28 B header + 260 B payload), see [Spec - CRS Format](Spec%20-%20CRS%20Format.md).
- Flash holds **two copies**, slots A and B, at the end of flash.
- Each copy is preceded by a 32-byte **slot header**, used only for:
  - the **commit marker** (power-loss safety),
  - **newest selection** (`seq`, a monotonic counter),
  - basic sanity (`crs_len` and magic).

The boot-time reader only has to:
- read the slot header and CRS bytes of A and B,
- validate the CRS,
- pick the newest valid slot by `seq`.

---

## 2) Flash placement (constants)

Board-specific constants, generated by `kb_firmware/build.rs` from `kb_firmware/boards/<board>/flash_layout.rs` and exported to the host scripts in `kb_firmware/target/crs_artifacts/flash_layout.env`:

| Constant | STM32G474CB (single bank) |
|---|---|
| `FLASH_ERASE_PAGE_SIZE` | 4096 |
| `CFG_SLOT_SIZE` | 4096 (one erase page) |
| `CFG_SLOT_A_BASE` | `0x0801_E000` |
| `CFG_SLOT_B_BASE` | `0x0801_F000` |
| `LED_STATE_FLASH_PAGE_BASE` | `0x0801_D000` ([LED journal](Spec%20-%20LED%20Runtime%20State%20Persistence.md), the page below slot A) |
| `FLASH_END` | `0x0802_0000` |

The slots sit at the **end of flash**, so the firmware can grow without moving them. `memory.x` reserves the last 12 KiB (LED journal + A + B) so the linker can't place code there.

**Policy (v1):** each slot is **exactly one erase page**. That keeps A/B writes and "invalidate a slot by erasing it" simple and independent of each other.

---

## 3) Per-slot layout

```text
SLOT_X_BASE:
  +0x0000  SlotHeader (32 bytes)
  +0x0020  CRS bytes (288 bytes)
  +0x0140  padding up to CFG_SLOT_SIZE (0xFF, erased flash)
```

- The slot header is fixed at **32 bytes**.
- The CRS starts at fixed offset **0x20** (32), which keeps it aligned to the 64-bit flash programming unit.

---

## 4) SlotHeader v1 (32 bytes): byte layout

All fields are **little-endian**, stored as raw bytes in flash.

| Offset | Size | Field | Meaning |
|---:|---:|---|---|
| 0x00 | 4 | `slot_magic` | ASCII `"SLO1"` (bytes `53 4C 4F 31`), i.e. u32 LE `0x314F4C53` |
| 0x04 | 2 | `hdr_version` | Slot header format version. Must be `1` |
| 0x06 | 2 | `reserved0` | Must be `0` |
| 0x08 | 4 | `seq` | Monotonic sequence counter. Higher = newer |
| 0x0C | 4 | `crs_len` | Must be `288` |
| 0x10 | 4 | `committed` | Commit marker (see [§5](#5-commit-marker-semantics)). Decides whether the slot is usable |
| 0x14 | 4 | `reserved1` | Must be `0` |
| 0x18 | 4 | `reserved2` | Must be `0` |
| 0x1C | 4 | `reserved3` | Must be `0` |

**Header size:** 0x20 (32 bytes). `committed` and `reserved1` form one 64-bit double word (`0x10..0x17`), so the commit can be programmed in one step.

---

## 5) Commit marker semantics

Flash programming can only clear bits (1 → 0); setting them back (0 → 1) needs an erase. On the STM32G4 each 64-bit double word can be programmed only **once** between erases.

So `committed` is defined as:

- After erase: `committed = 0xFFFF_FFFF` ⇒ **not committed**
- Final step of a successful write: programmed to `0x0000_0000` ⇒ **committed**

A commit is therefore a one-way operation within one erase cycle, and a write interrupted at any point before it leaves the slot uncommitted.

---

## 6) Slot validity (reader rules)

A slot is **valid** if all of the following hold:

1) Slot header checks:
- `slot_magic == "SLO1"`
- `hdr_version == 1`
- `crs_len == 288`
- `committed == 0x0000_0000`
- reserved fields: not checked by the reader (writers write 0)

2) CRS checks ([Spec - CRS Format](Spec%20-%20CRS%20Format.md)):
- CRS magic `"CRS1"` (LE `0x31535243`)
- schema version = 1
- len = 260 (payload length)
- `fw_compat_id` matches the firmware's `FW_COMPAT_ID`
- CRC32 matches (payload only, 260 bytes)

The CRS header's `flags` field is reserved and written as 0, but the reader does not check it.

If the slot header passes but the CRS fails, the slot is invalid. An uncorrectable flash ECC error while reading (a double word torn by a power loss mid-program) also makes the slot invalid (`SlotError::FlashEcc`) instead of hanging the MCU.

Slots read at boot are not run through the semantic validator (`validate_payload`); that runs on every WebHID save and in `crs-pack`.

---

## 7) Slot selection algorithm (boot)

1) Evaluate the validity of slot A and slot B ([§6](#6-slot-validity-reader-rules)).
2) If both are valid: select the slot with the **higher `seq`** (tie → slot A).
3) If only one is valid: select it.
4) If none is valid: **DisabledFallback**. Inputs are disabled and the LED output is held low; USB, the console and the configurator keep working, and diagnostics show the reason.

The firmware's built-in template (the configurator's "suggested setup") is deliberately **not** used here: unresponsive controls expose the problem, while an unexpected mapping would hide it. Rationale: [ARCHITECTURE §2.3](../ARCHITECTURE.md#23-no-valid-configuration-disabledfallback).

---

## 8) Writer rules

### 8.1 Prepare the CRS blob
- 288 bytes of CRS v1 (`crs-pack pack`, or the configurator's export).

### 8.2 Choose a target slot
- **Firmware (WebHID save):** always the non-selected slot (slot A when none is selected), `seq = max(valid seq) + 1` (1 when no slot is valid).
- **SWD (`embed_with_cfg.sh`):** the chosen slot (`--slot A`, default, or `--slot B`) with `seq = 1`; the other slot and the LED journal page are written as zeros, so only one slot is valid afterwards.

### 8.3 Writing a valid slot
1) Erase the slot page.
2) Program the slot header:
   - `slot_magic = "SLO1"`
   - `hdr_version = 1`
   - `seq` (see [§8.2](#82-choose-a-target-slot))
   - `crs_len = 288`
   - `committed` double word (`0x10..0x17`) left erased; programmed to `0x0000_0000` last (see **Order**)
   - reserved fields zero
3) Program the CRS bytes at offset `+0x20` (32).
4) Firmware writer: ECC-checked read-back compare, program the `committed` double word to zero (`committed = 0`, `reserved1 = 0`), then re-run the boot selector and require it to pick the new slot with identical bytes.

**Order:** a power-loss-safe writer programs the `committed` double word **last**, after verifying everything else (the firmware does). For SWD flashing the order doesn't matter, as long as the final bytes satisfy [§6](#6-slot-validity-reader-rules); the SWD script writes the whole region as one verified image.

### 8.4 Testing A/B selection
- Flash slot A with `seq = 1` and slot B with `seq = 2` (both committed): the firmware must pick slot B, provided both CRS blobs validate.

### 8.5 Invalidating a slot
- Erase the slot page (`committed` becomes `0xFFFF_FFFF`), or
- overwrite the page with zeros in one erase + program pass (what `embed_with_cfg.sh` does to the other slot).

---

## 9) Reserved space policy

- `reserved*` fields must be zero.
- Future revisions may define new fields, but:
  - `slot_magic` stays `"SLO1"` for v1,
  - `hdr_version` increments for new layouts,
  - a v1 reader rejects `hdr_version != 1` (safe).

---

## 10) What the firmware hardcodes

Hardcoded (shared with `crs_format`):
- slot header constants and offsets: `SLOT_HDR_LEN = 32`, `SLOT_CRS_OFFSET = 32`, `TOTAL_LEN = 288`;
- slot header magic / version / length / commit semantics;
- the CRS validation rules.

Not part of the slot format:
- how a slot was written (SWD or WebHID);
- any UI or status conventions.

---

## Appendix A — Field encodings

- `"SLO1"` magic: bytes `53 4C 4F 31` (ASCII), stored as little-endian u32 `0x314F4C53`.
- `committed`:
  - erased: `FF FF FF FF` (not committed)
  - committed: `00 00 00 00`
